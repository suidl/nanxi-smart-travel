## 一、项目概述

楠溪智游面向楠溪江家庭自由行游客，把“同行人、天数、预算、偏好、步行强度和出行日期”等需求转成可检查的约束，调用天气、景点检索、路线估算、预算核算和行程校验工具，生成逐日、逐站时间轴。途中遇到降雨、闭园等变化时，系统保留已完成的节点，只对当前所选日期的剩余行程重新决策。评委可访问 [在线体验版](https://naxi-travel-ai.netlify.app) 查看已发布的一日游流程；本地增强版已支持 1—5 天、自定义自然语言重生成与逐日切换，尚未发布到该网址。

本项目选择赛道一“人工智能体（AI Agent）”命题二“AI Agent × 永嘉特色产业”的文旅智能导览方向。赛事说明明确鼓励结合永嘉景区、文化点位和民俗传播，开展旅游资源整合、需求解析、路线规划与定制导览。楠溪智游聚焦其中最可验证的一环：从需求到可执行行程，再到途中变化后的持续决策。

## 二、问题与目标用户

楠溪江山水、古村及人文点位分布较广。自驾和家庭自由行用户在出发前需要同时权衡路程、天气、开放信息、老人儿童体力和总预算；出发后还会遇到天气变化或临时闭园。普通检索或聊天式推荐往往只给景点清单和文字建议，难以把多个约束统一到同一条可执行时间线上，也难以保证发生变化时不改写已经完成的现实。

首期目标用户是带老人或儿童的楠溪江自由行游客；第二类潜在用户是希望维护路线、内容和客流引导策略的景区、乡村及文旅运营方。首版不依赖任何企业私有数据或合作资源，避免“没有商家数据就无法演示”的问题。

## 三、产品方案与业务闭环

用户输入或修改出发地、日期、1—5 天行程天数、人数、偏好、预算与步行强度后，Agent 依次完成六个步骤：约束理解、逐日天气查询、景点筛选、路线估算、预算核算、可执行性检查。结果不是一段不可操作的文案，而是行程驾驶舱：逐站时间、景点说明、地理位置示意、费用拆分、风险提示、数据来源与执行轨迹同屏可见。

用户选择“情况有变”并触发降雨、闭园、体力下降或预算变化后，系统识别所选日期已完成与未完成节点，保留其他日期及已完成记录，重新选择后续节点并更新路线、时间及预算。页面不提供缺乏实时道路数据支撑的“拥堵重排”入口。用户随后可保存本地状态、导出中文 PDF、生成 ICS 日历或复制脱敏云端分享链接。完整业务闭环为“提出需求 → 查询与规划 → 校验 → 出行使用 → 情况变化 → 局部重排 → 导出分享”。

当前示范场景为从温州南站出发，1 名成人、1 名儿童和 1 名老人同行，预算 1200 元，偏好山水与古村、低步行强度。评委无需登录或准备数据即可操作。

## 四、AI Agent 的自主性与工具链

系统将大模型用于自然语言约束理解，不把时间、预算和安全性判断交给模型“凭感觉”决定。在线版通过 Netlify AI Gateway 调用模型，把非结构化需求映射成受限的结构化字段；服务异常时明确降级为本地规则解析。接下来由确定性工具执行景点检索、路线估算、费用计算和规则校验，形成“模型理解 + 工具执行 + 规则兜底”的组合。工具轨迹展示每一步的输入摘要和结果，便于评委复核。

现有工具与职责如下：

| 环节 | 当前实现 | 用户可见证据 |
|---|---|---|
| 约束理解 | AI 解析偏好、步行强度等，严格合并到原始请求 | 解析来源与摘要 |
| 天气查询 | Open-Meteo 代理；逐日查询，失败时标明演示天气 | 所选日期天气摘要、降雨风险及来源标记 |
| 景点筛选 | 从 27 条本地点位记录按偏好、适宜性筛选 | 候选数量、站点来源 |
| 路线估算 | 基于点位坐标估算距离与顺序 | 地理位置示意、全程预计路程；不冒充道路导航 |
| 预算核算 | 按人数、天数和节点成本估算，每日保留最低餐饮额度与预备费用 | 费用拆分、预算差额；明确未含住宿和返程交通 |
| 行程校验 | 检查开放信息、天气、步行强度与预算风险 | 明确警示与出发前复核提示 |
| 局部重排 | 锁定已完成节点，仅替换剩余安排 | 变更摘要、保留标识、新路线与预算 |

大模型调用仅发生在需要解释用户表达的入口；可由规则完成的计算与约束验证不重复调用模型。这降低运行成本，也使结果更可解释。执行轨迹展示各阶段结果，不展示未经实际计量的耗时。

## 五、永嘉特色与差异化

首版整理了 27 条永嘉相关点位数据，覆盖山水、古村、文化、美食、交通等类型，每条记录配置来源地址及资料日期。这里的来源标记用于便于复核，不代表票价、营业时间已经获得景区实时授权；存在不确定性的字段会要求游客出发前再次核实。

与通用旅游问答相比，楠溪智游的差异并非“更会写推荐词”，而是能把永嘉文旅点位、家庭出行约束与动态事件连接成同一条业务链。典型例子是午后阵雨：已到过的太平岩不会被重新安排，后续户外点位被替换为适合雨天的文化或古村体验，费用和路线同步改变。这一“已发生节点不可改写”的约束适用于县域景区串联、乡村游和民宿周边路线等场景，具有可复制性。

## 六、用户体验与成果形态

产品采用浏览器访问，不要求安装 App。创建页预填评委场景，可直接开始；本地增强版还允许选择 1—5 天，或在驾驶舱输入“双人五日游、预算 6000”等需求并在当前页重生成，结果显示实际新增、移除的节点及逐日安排。驾驶舱汇总路线、时间轴、预算和工具轨迹；发生变化时，用户通过明确的事件入口操作，结果标示保留节点与替换节点。页面已在桌面视口和 390×844 手机浏览器视口检查，手机页面无横向溢出；尚未在实体手机设备进行验证。

可交付成果包括公网 Web 应用、可编辑项目材料、演示截图、中文 PDF 行程样例、ICS 日历样例，以及可复现的测试脚本。导出的示例行程仅为演示，不代表真实预订或票价承诺。

## 七、技术实现与验证

前端为 React + TypeScript；服务端使用 Netlify Functions；分享数据使用 Netlify Blobs；天气由 Open-Meteo 提供；约束理解由 Netlify AI Gateway 调用模型。项目采用前后端分层，天气、AI、分享接口不可用时均有明确异常或降级处理。分享仅保存必要的行程信息，并过滤不应公开的敏感字段。

截至 2026 年 9 月 13 日，本地增强版 53 条单元/组件测试、3 条本地浏览器流程通过，TypeScript/Vite 与 Netlify Functions 构建通过。此前的公网版本已完成 1 条浏览器流程，`/api/plan` 曾返回 `source: ai`，天气与分享接口也曾实测；这些结果不能证明本次增强版已在公网生效。正式提交前必须部署增强版，并重新验证在线 AI 改线、五日游、逐日天气、导出和分享。这些数字是开发验证结果，不是用户规模或商业成效。

## 八、OPC 轻量创业模式与商业化路径

项目适合“个人主创 + AI 辅助研发 + 云服务”的轻量起步方式：首版基于公开资料建立点位库，以自动化测试和云部署降低原型验证成本，不以线下渠道或企业数据接入作为成立前提。AI 在需求解析、开发辅助和材料生产中提高效率，但路线计算、校验逻辑和输出责任仍由主创人员控制。

短期采用游客免费体验，验证生成完成率、重排使用率、导出率和问题反馈；中期面向景区、乡村运营方提供经授权的内容维护、路线配置和客流引导后台；长期在确保推荐透明、不影响安全约束的前提下探索 SaaS 服务费或合规导览合作。本计划为商业假设，尚无付费客户、签约伙伴或收入，申报材料不作相反暗示。

## 十、数据、合规与风险边界

1. 点位资料来自公开来源，引用链接和资料日期随数据保留；涉及价格、开放时间等变动信息均提示复核。
2. 现阶段路线距离基于坐标估算，不是实时驾车导航；导航入口跳转第三方地图搜索，实时路况和到达时间以地图为准。
3. 当前没有支付、订票、房态或交易接口，不以推荐结果冒充库存与最终价格。
4. 天气和模型不可用时显式标记降级；演示情境与真实天气严格区分。
5. 云端分享执行脱敏；正式面向公众扩大使用前，需进一步完成数据保留期限、删除机制和安全审查。
6. 所有商业推荐须明显标识，不得覆盖天气、体力、预算与开放风险校验。
